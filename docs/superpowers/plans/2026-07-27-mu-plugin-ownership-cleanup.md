# SiteIntelix MU Plugin Ownership and Cleanup Implementation Plan

> **For Codex:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Remove only verified SiteIntelix MU bootstraps when their module, the plugin, or the plugin installation is deactivated, while showing useful metadata for SiteIntelix MU files in WordPress.

**Architecture:** Add one fail-closed MU-file ownership manager and route every cleanup path through it. The manager checks a fixed filename allowlist, explicit approved directories, non-symlink regular files, and content signatures before deletion; generation remains in the existing Debug Log and Safe Mode classes.

**Tech Stack:** WordPress/PHP, Node.js built-in test runner, existing SiteIntelix structural tests.

## Task 3: Implement the fail-closed MU ownership manager

**Files:**
- Create: `wp-content/plugins/siteintelix/includes/class-siteintelix-mu-files.php`
- Test: `wp-content/plugins/siteintelix/tests/mu-files-cleanup.php`

**Step 1: Define the public cleanup API**

Add `SITEINTELIX_MU_Files` with:

```php
const TYPE_DEBUG        = 'debug';
const TYPE_SAFE_MODE    = 'safe_mode';
const TYPE_SAFETY_GUARD = 'safety_guard';

public static function remove_type( $type );
public static function remove_all();
```

Both methods return:

```php
array(
	'removed'   => array(),
	'preserved' => array(),
	'failed'    => array(),
);
```

**Step 2: Implement an explicit definition allowlist**

Use only these filenames and signatures:

- `siteintelix-debug-capture.php`
  - current signature: `SiteIntelix Debug Capture` and `siteintelix_debug_capture_enabled`
  - legacy signature: `SITEINTELIX_ENABLE_DEBUG_CAPTURE_OPTION` and `siteintelix_debug_capture_enabled`
- `siteintelix-safe-mode.php`
  - `SiteIntelix Safe Mode` and `siteintelix_safe_mode_hash_token`
- `siteintelix-plugin-safety-guard.php`
  - `SiteIntelix Plugin Safety Guard` and `siteintelix_psg_filter_active_plugins`

A file is owned when every marker in at least one signature set matches. A filename alone is never sufficient.

**Step 3: Resolve only approved directories**

Return normalized, deduplicated versions of:

- `WPMU_PLUGIN_DIR`
- `WP_CONTENT_DIR . '/mu-plugins'`

Do not recurse, discover sibling directories, or follow arbitrary paths. Construct each candidate as an exact approved directory plus an allowlisted filename.

**Step 4: Preserve unsafe or unverifiable candidates**

Before reading or deleting:

- Reject symlinks with `is_link()`.
- Require `is_file()` and `is_readable()`.
- Read the complete candidate safely.
- Preserve the candidate when reading fails or signatures do not match.

Missing files are successful no-ops and do not need a result entry.

**Step 5: Delete and verify**

Delete an owned candidate with `wp_delete_file()`. Then verify that neither a file nor symlink remains at that exact path:

- Add the path to `removed` only when it is gone.
- Add the path to `failed` when it remains.
- Never delete a directory.

**Step 6: Run the focused cleanup test**

Run:

```bash
php wp-content/plugins/siteintelix/tests/mu-files-cleanup.php
```

Expected: PASS for ownership, foreign-file, type-isolation, directory, symlink, and result-shape cases.

## Task 4: Route module and plugin lifecycle cleanup through the manager

**Files:**
- Modify: `wp-content/plugins/siteintelix/siteintelix.php`
- Modify: `wp-content/plugins/siteintelix/uninstall.php`
- Modify: `wp-content/plugins/siteintelix/includes/class-siteintelix-mu-debug.php`
- Modify: `wp-content/plugins/siteintelix/includes/modules/safe-mode-debugger/class-siteintelix-safe-mode-debugger-module.php`
- Test: `wp-content/plugins/siteintelix/tests/structural.test.mjs`
- Test: `wp-content/plugins/siteintelix/tests/mu-files-cleanup.php`

**Step 1: Load the manager for normal runtime**

Require `includes/class-siteintelix-mu-files.php` unconditionally near the beginning of `siteintelix_load_includes()`, before module-specific cleanup classes use it.

For activation/deactivation callbacks, defensively require the class by its exact plugin path when it has not already loaded.

**Step 2: Replace Debug Capture cleanup**

Change `SITEINTELIX_MU_Debug::remove_mu_plugin_file()` to call:

```php
SITEINTELIX_MU_Files::remove_type( SITEINTELIX_MU_Files::TYPE_DEBUG );
```

Translate a non-empty `failed` result into the method’s existing `WP_Error` contract so module-level UI can report a cleanup problem. Do not use `WP_Filesystem` deletion in this method.

**Step 3: Add Safe Mode cleanup**

After stopping the current user session in `SITEINTELIX_Safe_Mode_Debugger_Module::deactivate()`, call:

```php
SITEINTELIX_MU_Files::remove_type( SITEINTELIX_MU_Files::TYPE_SAFE_MODE );
```

Do not remove Debug Capture or any foreign bootstrap when only Safe Mode is disabled.

**Step 4: Add full deactivation cleanup**

In `siteintelix_deactivate()`:

- Preserve existing Email Log unscheduling.
- Set `SITEINTELIX_MU_DEBUG_OPTION` to disabled.
- Stop the current Safe Mode session when the Safe Mode class is available.
- Call `SITEINTELIX_MU_Files::remove_all()` so current and legacy SiteIntelix MU files are removed from both approved directories.

Do not delete SiteIntelix settings, tables, logs, snippets, or custom-code records on deactivation.

**Step 5: Replace uninstall’s one-file deletion**

At the start of `uninstall.php`, before option cleanup:

```php
$siteintelix_mu_files_class = __DIR__ . '/includes/class-siteintelix-mu-files.php';
if ( file_exists( $siteintelix_mu_files_class ) ) {
	require_once $siteintelix_mu_files_class;
	SITEINTELIX_MU_Files::remove_all();
}
```

Remove the old direct Debug Capture deletion block. Leave all third-party files and `wp-config.php` untouched.

**Step 6: Run focused and structural tests**

Run:

```bash
php wp-content/plugins/siteintelix/tests/mu-files-cleanup.php
node --test wp-content/plugins/siteintelix/tests/structural.test.mjs
```

Expected: PASS.
